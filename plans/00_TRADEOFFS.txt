D-01  ТРАНСПОРТ: UDP unicast-репликация                                  [04,10]
--------------------------------------------------------------------------------
вместо      IP multicast
почему нет  VPC не форвардит multicast вообще. Единственная нативная опция —
            TGW multicast domains: ~150-200 us one-way. AWS сам пишет
            "may not be suitable for high-frequency trading".
            Overlay (GRE/VXLAN) — та же head-end репликация плюс инкапсуляция.
остаток     multicast живёт флагом --transport udp-mcast для их "реального L2
            стенда": там fan-out становится O(1) и FEC делится между всеми.
            Отклонённый TGW с цифрой идёт в райтап — это признак строгости.

D-02  БЕЗ DPDK                                                              [12]
--------------------------------------------------------------------------------
вместо      DPDK ENA PMD
почему нет  AWS публикует свой замер: p50 25.6us / p99 28.2us на m8a.metal-24xl
            с DPDK. Настроенный kernel UDP отстаёт на 2-4us. Это ~10% пути.
            Цена: привязка ENI к vfio-pci; судья ошибается порядком -> теряет
            SSH -> инстанс недоступен. README: невоспроизводимость = основание
            для дисквалификации.
остаток     цифру AWS кладём в райтап как потолок и показываем, насколько
            близко подошёл kernel-путь.

--------------------------------------------------------------------------------
D-03  БАТЧИНГ: opportunistic drain                                       [04,09]
--------------------------------------------------------------------------------
вместо      фиксированный батч N сообщений
почему нет  фикс.батч добавляет fill latency ПЕРВОМУ сообщению напрямую:
            23 сообщения @1M msg/s = 23us ожидания = всё время на проводе.
как работает  забираем из ring'а всё, что есть, шлём, повторяем.
            batch = rate x send_cost сам собой: ~1 @100k, ~3 @1M.
            gap между датаграммами ~3us @1M. Ноль настроечных ручек.
следствие   именно малый gap делает стаггер-FEC дешёвым (см. D-04) — эти два
            факта связаны, в райтапе подавать вместе.

--------------------------------------------------------------------------------
D-04  ИЗБЫТОЧНОСТЬ: дублирование по 2-3 разным src-портам               [07,03]
--------------------------------------------------------------------------------
вместо      NACK + ретрансмит как основной механизм
почему нет  при p=1% восстановление стоит T_detect + 2D ~ 57-65us при p50 26us.
            И происходит это РОВНО на p99 — т.е. хвост взрывается точно на
            измеряемом перцентиле. Трёхкратный взрыв.
как работает  latency = min(L_A, L_B). Разные src-порты дают три декорреляции
            разом: (1) VPC ECMP хеширует по 5-tuple -> разные физ.пути;
            (2) разные RSS-бакеты -> разные RX-очереди -> разные CPU приёмника;
            (3) разные TX-потоки/ядра.
цена        2x-3x полосы. При 40 B/сообщение и 1M msg/s это 0.32 Gbps из 12.5 —
            полоса почти бесплатна, тратим её на избыточность.
второй порядок  2x оставляет остаток p^2 = 1e-4 = РОВНО граница p99.99.
            То есть 2x чинит p99 и p99.9, но p99.99 остаётся ~RTT.
            Чистый p99.99 при 1% потерь покупает только 3x.
            Вот настоящая причина делать кодек (D-12): не сдвиг насыщения,
            а чтобы 3x стало по карману.
допущение   независимость путей НЕ доказана. Проверяет эксперимент 03.
            Если пути зависимы — переходим на ветку B (хвост host-side).
NACK        остаётся страховкой для остатка p^2/p^3 и пачек.

--------------------------------------------------------------------------------
D-05  БЕЗ REED-SOLOMON, XOR только как tier под нагрузкой                   [07]
--------------------------------------------------------------------------------
вместо      RS(8,2) через ISA-L
почему нет  RS разделяет фундаментальную проблему XOR: recovery latency СНИЗУ
            ограничена временем набора окна ~ (k/2)*g. Encode-стоимость тут ни
            при чём, ISA-L быстрый. RS выигрывает только когда упёрлись в
            полосу — а мы на 0.32 Gbps из 12.5 туда не попадаем.
            Два дня работы под режим, в который мы не заходим.
остаток     анализ с цифрами в райтап. "Реализовали XOR, посчитали RS(8,2),
            отвергли оба, потому что recovery окно-связан, а полоса ни разу не
            была ограничением" — сильнее, чем отгрузить RS.

D-06  ДОСТАВКА: out-of-order немедленно                                  [04,07]
--------------------------------------------------------------------------------
вместо      ресеквенсинг-буфер (доставка строго по порядку)
почему нет  consumer.cpp:97-120 читает ring ПО ИНДЕКСУ СЛОТА, не по seq_id,
            а expected = last_seq - first_seq + 1. Переупорядочивание ему
            безразлично. Буфер добавил бы латентность ВСЕМ сообщениям ради
            свойства, которое никто не измеряет.
остаток     флаг --ordered с ограниченным буфером для честности + обе кривые в
            ноутбуке. Восстановленные сообщения публикуем как приходят.

D-07  ДЕДУП ОБЯЗАТЕЛЕН С v0                                                 [04]
--------------------------------------------------------------------------------
вместо      без дедупа (раз consumer терпит переупорядочивание)
почему нет  любая избыточность (D-04) доставляет дубли. consumer считает
            received по каждому слоту, а expected = last - first + 1.
            Дубль -> received > expected -> dropped уходит в минус, перцентили
            считаются по удвоенной выборке. Это hard correctness gate.
как         битмап по seq_id, окно ~200 мс, размер под L2.

D-13  ПРЕДИКТОРЫ ТОЛЬКО ГЕНЕРИЧЕСКИЕ                                        [08]
--------------------------------------------------------------------------------
вместо      захардкодить константы, вычитанные из producer.cpp
почему нет  это ровно то, что судья-HFT назовёт подгонкой под бенчмарк.
            Плюс README грозит сменить payload на "произвольные сообщения от
            единиц до сотен байт" — подогнанный кодек сломается.
правило     предиктор использует только то, что есть в потоке: другие поля того
            же сообщения или предыдущие значения того же поля. Никогда —
            константу из producer.cpp.
проверка что правило рабочее  checksum = (u32)(seq * 2654435761u),
            producer.cpp:161 — ни один генерик его не берёт -> шлём 4 байта
            явно. Эта строка и доказывает, что правило не декоративное.
механика    каждый предиктор = 1 бит + проверка при кодировании + откат на
            явное значение при несовпадении. Шкала price_ticks выучивается в
            рантайме перебором {1,10,...,1e9}. Требует -ffp-contract=off, но
            verify-and-fallback делает нас корректными и при нарушении.

D-14  ПОТЕРИ: свой детерминированный дроппер + netem                        [05]
--------------------------------------------------------------------------------
вместо      только tc netem
почему нет  netem зависит от версии ядра, недетерминирован, требует root и
            сидит в TX-пути (свой джиттер = загрязнение измерения).
как         дроппер внутри receiver'а, ключ hash(dgram_id) < threshold.
            Точно воспроизводим, кернел-независим, судья повторит БЕЗ root.
остаток     netem (loss random + gemodel) всё равно гоняем ради реализма,
            результаты из обоих в райтап. Gilbert-Elliott обязателен: реальные
            потери пачками, и именно пачки ломают одиночный parity.

D-15  ЧАСЫ: PHC + двунаправленная сумма                                     [02]
--------------------------------------------------------------------------------
вместо      RTT/2 (пинг-понг)
почему нет  RTT/2 требует предположения о симметрии пути, которое ничем не
            проверяется.
как         гоняем пайплайн в ОБЕ стороны одновременно. L_AB + L_BA точно
            свободно от смещения часов БЕЗ допущения о симметрии.
            Любой конкурент с заявкой "5 us one-way" обязан предъявить сумму 10.
            А (L_AB - L_BA)/2 = -offset при симметрии -> независимая оценка,
            сверяем с ClockBound. Сошлись в пределах 2us -> доказано дважды.
точность    PHC даёт смещение в единицах us, 5/95 перцентили за 15 мин редко
            вне +-2us. Против one-way 26us это ~8% на p50 и ~0 на p99-p50.

D-16  ИНСТРУМЕНТАЦИЯ: гистограммы всегда + сэмплы по seq_id % S             [06]
--------------------------------------------------------------------------------
вместо      полная запись всех стадий для каждого сообщения

D-17  NACK БЕЗ SRM-ПОДАВЛЕНИЯ ПРИ UNICAST                                   [07]
--------------------------------------------------------------------------------

почему нет  при unicast-репликации три получателя — три РАЗНЫХ 5-tuple, потери

            экономия полосы, но без встроенной задержки, как у SRM.
в райтап    сказать явно — многие реализуют SRM рефлекторно.

D-23  FAN-OUT: один sendmmsg до N=4, потоки выше                            [10]
--------------------------------------------------------------------------------
вместо      поток+сокет на получателя с самого начала
почему нет  sendmmsg на неподключённом сокете с [dst1..dstN]: ~0.5-1us на
            назначение в ядре -> перекос 1-3us между первым и последним, и
            ноль дополнительных ядер.
            Потоки дают перекос ~0.2us, но ценой N ядер. При N<=3 (базовый
            сценарий жюри) это не окупается.

            получатель систематически последний.
метрика     перекос между получателями репортим отдельно — этого не покажет
            никто.

D-25  АДАПТИВНЫЙ КОНТРОЛЛЕР БЕЗ РУЧНЫХ КОНСТАНТ                             [09]
