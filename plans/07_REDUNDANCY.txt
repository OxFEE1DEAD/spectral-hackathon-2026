07  REDUNDANCY — восстановление потерь            HEADLINE
    дни 8-11 (32 ч по ветке A / 16 ч по ветке B)
================================================================================
решения: D-04 дублирование, D-05 без RS, D-17 без SRM, D-25 Δ из данных
файлы: transport/include/{redundancy.h, nack.h}

БАЗА ДЛЯ РАСЧЁТОВ
  one-way D ~ 26 us (p50), RTT ~ 52 us, gap между датаграммами g ~ 3 us @1M msg/s

СРАВНЕНИЕ СХЕМ (recovery latency, а не только оверхед)

  схема                     оверх.  recovery @1M   остаток при p=1%
  ------------------------------------------------------------------------
  NACK + ретрансмит          1.0x   57-65 us       1e-4 нужен 2-й раунд ->
                                                   2 RTT ~130 us на p99.98
  дублирование 2 порта Δ=0   2.0x   0 (это min)    p^2 = 1e-4
  2 порта + стаггер Δ=1  *   2.0x   3 us           1e-4, пачки ~1e-3
  3 порта, стаггеры 0/1/3 ** 3.0x   0 / 3 / 9 us   p^3 = 1e-6, пачки ~1e-5
  XOR окно k=8               1.125x 12 us ср/27 худ 2.8e-3

КАК ЭТО ЧИТАТЬ
  При p=1% NACK кладёт p99 на 57-65 us при p50 26 us — трёхкратный взрыв,
  и происходит он РОВНО на измеряемом перцентиле. Дублирование держит
  p99 ~ p50. Этот контраст — headline-график всей работы.

РЕЗУЛЬТАТ ВТОРОГО ПОРЯДКА (никто не посчитает)
  2x оставляет остаток p^2 = 1e-4 = РОВНО граница p99.99.
  То есть 2x чинит p99 и p99.9, но p99.99 остаётся ~RTT.
  Чистый p99.99 при 1% потерь покупает ТОЛЬКО 3x.
  3x от 40 B/сообщение при 1M msg/s = всё ещё < 1 Gbps из 12.5.
  -> вот настоящая причина делать кодек (файл 08): не сдвиг насыщения,
     а чтобы 3x стало по карману.

ПОДТВЕРЖДЕНО ЛОКАЛЬНО (netns, файл 00A) — механика, не допущение
  дроппер с независимыми потерями 1% на копию:
    streams=1  0.9896%    streams=2  0.0119% (=p^2)    streams=3  0.0000%
    p50 = 1292 / 1292 / 1291 нс — избыточность не стоит латентности
  netem gemodel (пачки), streams=2 против streams=1: 2.92% против 4.92%.
  ВСЕГО -40%, не p^2. Копии идут спина к спине, пачка сносит обе.
  -> Δ=0 достаточно для bernoulli и бесполезен на пачках. Ниже — почему Δ
     обязан выводиться из данных.

СТАГГЕР Δ ВЫВОДИТСЯ ИЗ ДАННЫХ [D-25]
  Δ = ceil(p95 длины пачки потерь) + 1, потолок Δ*g <= 20 us.
  netem loss random -> гистограмма даёт run=1 -> Δ=0, чистое хеджирование
  netem gemodel     -> run~3               -> Δ=3, ценой 9 us на резервной
  Одно число из измеренной гистограммы делает всю адаптацию.
  вместо подобранной константы: она сломается при смене профиля потерь,
  и выглядит как подгонка.

NACK — ТОЛЬКО СТРАХОВКА
  ловит остаток p^2/p^3 и пачки, обогнавшие Δ.
  детекция    таймер терпимости к переупорядочиванию
              T_d = 2 * ИЗМЕРЕННЫЙ разброс + запас.
              При двух путях это ~15-25 us, не 5. ИЗМЕРИТЬ, не угадывать.
              Публикуем сразу, не блокируемся [D-06] -> ожидание бесплатно.
  буфер       кольцо ЗАКОДИРОВАННЫХ датаграмм по seq, 200 мс.
              @1M x 40 B x 0.2 с = 8 МБ, на hugepages. Тривиально.
  heartbeat   current_max_seq раз в ~200 us -> ловим потерю в КОНЦЕ пачки,
              не дожидаясь следующих данных. Без этого хвост прогона гнилой.
  шторм       token bucket <=5% прямого потока на получателя; превысил ->
              поднимаем tier избыточности вместо ретрансмита [D-18]

FAN-OUT x NACK [D-17]
  unicast:   потери на 3 потоках независимы (разные 5-tuple) ->
             НИКАКОГО подавления, ретрансмит только запросившему.
             вместо SRM randomized-delay: добавит латентность за ноль пользы.
             В райтапе сказать явно — многие делают SRM рефлекторно.
  multicast: коалесцирование ремонтов в окне 100 us (дедуп NACK'ов на seq ->
             один multicast-ремонт). Та же экономия, без встроенной задержки.

БЕНЧМАРК ЭТОЙ СТАДИИ — ГЛАВНЫЙ ГРАФИК РАБОТЫ
  оси: loss {0, 0.01%, 0.1%, 1%, 2%} x {bernoulli, gemodel}
       x {NACK-only, dup2 Δ=0, dup2 Δ=adaptive, dup3, XOR k=8}
  метрика: p50/p99/p99.9/p99.99 + loss-aware перцентили [D-22]
  ожидаемая картина: у NACK-only p99 растёт с потерями почти линейно;
  у dup2 p99 и p99.9 плоские, p99.99 растёт; у dup3 всё плоское.
