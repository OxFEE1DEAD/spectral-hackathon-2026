  bench/vm-up.sh    Lima VM: Ubuntu 24.04.4, ядро 6.8.0, 6 vCPU, 8 GiB,

  bench/vm.sh       запуск команды в VM из корня репо

  ПОЧЕМУ VM, А НЕ DOCKER
    вместо: контейнер
    почему нет: Docker на Mac всё равно крутится внутри Linux-VM — контейнер
    не экономит слой, только отнимает права. Нужны свободные netns, tc/netem,
    sysctl, потенциально модули ядра.

  ПОЧЕМУ Ubuntu 24.04
    ровно целевой дистрибутив жюри -> команды в docs/REPRODUCE.md пишутся
    сразу против него и переносятся на AWS без правок.

  ПОЧЕМУ arm64, А НЕ ЭМУЛЯЦИЯ x86_64
    вместо: qemu-эмуляция ради совпадения с m7i
    почему нет: числа бессмысленны в обоих случаях, а нативная виртуализация
    итерируется в 10-20 раз быстрее. x86-специфики мало (rdtscp), она за
    #ifdef.
    ПОБОЧНАЯ ВЫГОДА: модель памяти ARM слабее x86 -> пропущенные
    acquire/release барьеры в lock-free кольце падают здесь, а не молча
    работают до AWS.

  ЗАМЕРЕНО: счётчик ARM generic timer = 23.9 МГц = 41.7 нс/тик.
  Грубо (на x86 TSC будет ~0.3 нс/тик), но для функциональной работы неважно.

--------------------------------------------------------------------------------
  bench/netns-up.sh    ns tx(10.0.0.1) <--veth, mtu 1500--> ns rx(10.0.0.2)

  Настоящие сокеты, настоящий сетевой стек ядра, настоящие потери.
  ПРОВЕРЕНО: baseline 0% -> netem 10% даёт 9% -> gemodel даёт пачки -> off 0%.

  нет фабрики. Числа только с AWS.

  ГРАБЛИ: netns изолирует ТОЛЬКО сеть. /dev/shm общий -> кольцо на стороне
  producer'а и кольцо на стороне consumer'а обязаны иметь РАЗНЫЕ имена.

  ГРАБЛИ: net.core.rmem_max/wmem_max НЕ неймспейсятся, ставятся глобально.

  Оффлоады (gro/gso/tso) на veth выключены: они склеивают датаграммы и
  прячут ошибки фрейминга, которые реальный NIC вскроет.

  transport/include/tsc.h     счётчик: x86 rdtscp / aarch64 cntvct_el0 /

  transport/include/hist.h    лог-линейная гистограмма, 7 sub-бит = 0.78%
                              ошибки, ~27 КБ; перцентиль = ВЕРХНЯЯ граница
                              бакета (никогда не приукрашиваем)
  transport/include/dedup.h   скользящий битмап по seq_id [D-07]
  transport/include/wire.h    заголовок датаграммы 32 B, kMaxDatagram=1472

  ПОЧЕМУ 1472, А НЕ 8900 (VPC держит jumbo)
    вместо: jumbo-кадры ради меньшего числа датаграмм
    почему нет: фрагментированная IP-датаграмма выживает только если выжили
    ВСЕ фрагменты -> эффективная потеря умножается на число фрагментов.
    Ровно наоборот тому, на чём стоит вся наша ставка. Jumbo — опция для
    same-subnet прогонов, не дефолт.

  ПОЧЕМУ сообщения НЕ пересекают границу датаграммы
    потеря датаграммы обязана стоить ровно тех сообщений, что внутри.
    Иначе одна потеря портит соседей — это и есть то, что README называет
    слабостью текущего формата.

  ТЕСТЫ: make -C transport test    (hist 26842 / dedup 1161 / wire 2916 / tsc)
         make -C transport sanitize  ASan+UBSan, всё зелёное
  Парсер wire читает недоверенные байты из сети -> тест режет датаграмму на
  КАЖДОМ смещении и проверяет, что разбор останавливается чисто.

БЛОК 2 — v0 TRANSPORT                                                [СДЕЛАНО]
--------------------------------------------------------------------------------
  transport/include/net.h      сокеты, sendmmsg на N назначений с ротацией,
                               recvmmsg батчем, busy-poll за feature detection
  transport/include/control.h  TCP-хендшейк (только setup); NACK и телеметрия
                               поедут по UDP — TCP дал бы head-of-line blocking
                               ровно при потерях, когда ремонт нужен срочнее
  transport/src/sender.cpp     opportunistic drain -> датаграмма -> N копий
  transport/src/receiver.cpp   recvmmsg -> parse -> дедуп -> publish, сразу
  bench/e2e-netns.sh           полный прогон через две netns
  bench/regress.sh             гейт на каждый коммит, без AWS

  ОПТИМИЗАЦИЯ, СДЕЛАННАЯ СРАЗУ: wire::Builder::append_ptr/append_commit.
  Sender читает слот SHM напрямую в TX-буфер -> минус одна копия 576 B на
  сообщение. Ничего не коммитится до append_commit, поэтому чтение,
  оказавшееся lapped посреди копирования, просто отбрасывается.

  ГРАБЛИ, ЗАКРЫТЫЕ В КОДЕ:
    - producer.cpp:229 делает shm_unlink на выходе И создаёт сегмент ДО
      ftruncate. Наивный open ловит обе гонки: то исчезающий сегмент, то
      нулевой длины (SIGBUS при первом касании). Ждём появления И размера.
      shm::Segment::open делает exit(1) при неудаче, поэтому проба обязана
      быть ДО него.
    - sender стартует с live_edge(). Иначе при подключении выплюнет в сеть
      весь накопленный backlog.
    - lapping producer-ring'а считается ОТДЕЛЬНЫМ счётчиком: это потеря ДО
      провода, и приписывать её транспорту нельзя.
    - дроппер ключуется на (dgram_id, stream_id), а не только на dgram_id.
      Иначе все копии датаграммы дропались бы вместе — ровно та корреляция,
      против которой избыточность и existует, и дублирование выглядело бы
      бесполезным при любом качестве реализации.

НАХОДКА: КРОСС-ДОМЕННЫЕ СТАДИИ НЕЛЬЗЯ МЕРИТЬ ЧЕРЕЗ КАЛИБРОВКУ
--------------------------------------------------------------------------------
  Первый прогон: 28% сообщений с ОТРИЦАТЕЛЬНОЙ задержкой подхвата, стадия
  S0->S7 собрала 1829 сэмплов из 190k.
  Причина: S0->S1 и S0->S7 пересекают границу доменов часов (producer штампует
  CLOCK_REALTIME, мы — тактами). Двухточечный фит за 20 мс на 24-МГц счётчике
  даёт ошибку слоупа ~2e-6 -> пара микросекунд дрейфа за секунду прогона.
  Против p50 подхвата в 167 нс этого хватает, чтобы перевернуть знак.

  ФИКС: не калибровать точнее, а не конвертировать вовсе. Кросс-доменные
  стадии читают CLOCK_REALTIME напрямую (та же одна операция чтения часов).
  Такты остаются для РАЗНОСТЕЙ внутри процесса, где слоуп сокращается.

  Калибровка остаётся нужной для сшивки с HW RX-таймстемпами в домене PHC.
  На AWS понадобится периодический рефит (файл 06).

  ПРОВЕРКА ПОСЛЕ ФИКСА: наш "до кольца" p50 = 1215 нс против consumer'а
  p50 = 1297 нс. Разница ~80 нс — его собственный опрос кольца. Сходится.

НАХОДКА: ДУБЛИРОВАНИЕ Δ=0 НЕ РАБОТАЕТ НА ПАЧКАХ                    [ВАЖНОЕ]
--------------------------------------------------------------------------------
  Детерминированный дроппер, независимые потери 1% на копию:
    streams=1  drop_rate 0.9896%   (p)
    streams=2  drop_rate 0.0119%   (p^2 = 0.01%)     <- ровно предсказание D-04
    streams=3  drop_rate 0.0000%   (p^3)
    p50 = 1292 / 1292 / 1291 нс — избыточность НЕ стоит латентности

  netem, реальные потери в ядре:
    bernoulli 1%, streams=2   0.0084%   работает идеально
    gemodel,      streams=1   4.92%
    gemodel,      streams=2   2.92%     ВСЕГО -40%, НЕ p^2

  Копии уходят спина к спине -> пачка сносит обе разом.
  Это эмпирическое подтверждение D-25: Δ обязан выводиться из ИЗМЕРЕННОЙ
  гистограммы длин пачек, а не быть нулём. Теперь это не бумажный аргумент.

  ЧЕГО ЭТО НЕ ДОКАЗЫВАЕТ: наш дроппер по построению роняет копии независимо.
  Независимы ли реально два src-порта на фабрике AWS — эксперимент файла 03.
  Локально проверена МЕХАНИКА, а не ДОПУЩЕНИЕ.
