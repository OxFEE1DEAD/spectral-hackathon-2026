# План: Spectral::Technologies — Low-latency data transfer (цель: 1 место)

## Контекст

Организаторы дают фиксированные концы системы: `harness/src/producer.cpp` (генерит market-data, штампует `seq_id` + `send_ts_ns`) и `harness/src/consumer.cpp` (меряет latency по этим штампам). Оба общаются через SHM broadcast ring (`harness/include/shm_ring.h`). Нам надо построить середину — `sender` (хост A) и `receiver` (хост B), которые тащат поток через реальную сеть.

Оценивают: e2e latency p50/p99/p99.9/p99.99 как функцию (а) rate до насыщения, (б) fan-out 1..3+. Главная дифференциация — **высокие перцентили и как хвост держится под нагрузкой**. Канал имеет 0.01–1% потерь. Воспроизводимость обязательна (невозможность воспроизвести = DQ). Стенд: AWS m7i/m8a, Ubuntu 24.04 или 20.04, ENA.

Дедлайн 30 августа 2026. Бюджет времени: ~160 ч (8 ч/день × 20 дней). Бюджет железа: в притык.

**Что уже установлено из чтения кода** (проверено построчно):

## Целевая архитектура

```
ХОСТ A                                                  ХОСТ B (×N)
┌──────────┐   SHM ring    ┌────────┐              ┌──────────┐   SHM ring   ┌──────────┐
│ producer │──1024 слота──▶│ sender │═══ UDP ═════▶│ receiver │─1024 слота──▶│ consumer │
│ (не наш) │               │        │  2-3 копии   │          │              │ (не наш) │
└──────────┘               └────┬───┘  разные      └────┬─────┘              └──────────┘
                                │      src-порты        │
                                └──── TCP control ──────┘
                                    (handshake, NACK, телеметрия)
```

**Горячий путь sender:** spin на producer-ring → opportunistic drain (сколько есть) → encode в TX-буфер → `sendmmsg` на N назначений × K копий → запись в retransmit-ring. Ноль аллокаций, ноль локов, ноль `printf`.

**Горячий путь receiver:** busy-poll `recvmmsg` → decode → дедуп по битмапу → publish прямо в слот consumer-ring (без промежуточной копии). Восстановленные позже сообщения публикуются как приходят — не переупорядочиваем.

**Холодные потоки** (отдельное ядро): NACK, телеметрия, адаптивный контроллер, снапшоты счётчиков.

### Ключевые решения и обоснования

| Решение | Почему |
|---|---|
| **UDP unicast-репликация по умолчанию** | VPC **не форвардит multicast**. Единственная нативная опция — TGW multicast domains, и AWS сам пишет, что это «may not be suitable for high-frequency trading»; замеряли ~150–200 µs one-way. Режим `--transport udp-mcast` держим для их «реального L2 стенда». Отклонённый вариант с цифрами в райтапе = признак строгости, а не дыра |
| **Opportunistic drain вместо фиксированного батча** | Фиксированный батч добавляет **fill latency** первому сообщению напрямую: батч из 23 сообщений при 1 M msg/s стоит первому 23 µs — сопоставимо со всем временем на проводе. Drain даёт batch ≈ rate × send_cost (~3 сообщения при 1 M/s), gap между датаграммами ~3 µs. Ноль настроечных констант |
| **Дублирование по разным src-портам** | Даёт три декорреляции разом: (1) фабрика VPC ECMP-хеширует по 5-tuple → разные физические пути; (2) разные RSS-бакеты → разные RX-очереди → разные CPU на приёмнике; (3) разные TX-потоки/ядра. Latency = `min(L_A, L_B)`. Если пути независимы, p99.99 от `min` = p99 одиночного пути |
| **Дедуп обязателен с v0** | Иначе `received > expected`, `dropped` уходит в минус, перцентили считаются по удвоенной выборке |
| **`-std=c++17`, ноль внешних зависимостей** | Ubuntu 20.04 (gcc 9, ядро 5.4) в списке целевых окружений, а DQ за невоспроизводимость — реальный риск. gcc 9 не тянет полный C++20. Для этого кода (сырые syscalls, атомики, memcpy) C++17 достаточен. `napi_defer_hard_irqs`, `SO_PREFER_BUSY_POLL` (5.11+), AF_XDP — за runtime feature detection с graceful fallback. *Если хочешь именно C++20 — это `-std=c++20` + требование g++-11 в инструкции для жюри; скажи, поменяю* |
| **DPDK не делаем** | AWS публикует свой замер: p50 25.6 µs / p99 28.2 µs на m8a.metal-24xl с DPDK. Настроенный kernel UDP отстаёт на ~2–4 µs. Это ~10% пути ценой высокого риска DQ (привязка ENI к vfio-pci, судья теряет SSH). В райтапе — цифра AWS как потолок и насколько близко мы подошли |
| **Reed-Solomon не делаем** | RS разделяет фундаментальную проблему XOR: **recovery latency снизу ограничена временем набора окна** (`(k/2)·g`). RS выигрывает только когда упёрлись в полосу, а на 12.5 Gbps с 40-байтными сообщениями мы туда не попадаем. Анализ в райтап, код — нет |
| **ENA Express выключен по умолчанию** | AWS сам предупреждает: «slight increase in median packet latency (**tens of microseconds**)» при лёгком трафике. Это удвоило бы p50. Но заявляет до 85% улучшения p99.9 под нагрузкой → один эксперимент на насыщении, результат в таблицу компромиссов |

## Как бенчмаркать: инструмент

### Разбиение бюджета латентности по стадиям

Это ядро ответа на «на что смотреть и когда куда лезть».

| # | Стадия | Часы | Замечание |
|---|---|---|---|
| S0 | producer штампует `send_ts_ns` | CLOCK_REALTIME, хост A | дано harness'ом |
| S1 | sender забрал из SHM ring | **TSC_A** | |
| S2 | encode завершён | TSC_A | |
| S3 | `sendmmsg` вернулся | TSC_A | |
| S4 | kernel TX software timestamp | CLOCK_REALTIME, A | `SOF_TIMESTAMPING_TX_SOFTWARE` через `MSG_ERRQUEUE`, **только на сэмплах** |
| S5 | **NIC HW RX timestamp** | домен PHC, хост B | `SO_TIMESTAMPING_NEW`, `ts[2]` |
| S6 | `recvmmsg` вернулся | **TSC_B** | |
| S7 | decode + publish в SHM | TSC_B | |
| S8 | consumer штампует `recv_ts` | CLOCK_REALTIME, B | из `--csv`, джойн по `seq_id` |

**Важно: у ENA хардварные таймстемпы только на RX.** TX — software через error queue. Значит «проводной» сегмент измеряется как `S5 − S4` и включает время driver→wire на хосте A. Это ограничение надо назвать в райтапе прямо, а не делать вид, что у нас чистое время провода. `ethtool -T eth0` покажет, что реально доступно — проверить в первый час.

HW packet timestamping появился в ENA-драйвере r2.15.0, **выключен по умолчанию**, а переключение вызывает кратковременный обрыв линка → включать до прогона, не во время.

### Правило приоритизации

> Считаем `spread(стадия) = p99.9(стадия) − p50(стадия)` по всем стадиям. **Идём в стадию с наибольшим spread.**

Среднее говорит о пропускной способности; spread говорит о джиттере, а приз — за джиттер.

### Дерево диагностики

| Наибольший spread | Обычные причины | Чем проверить | Чем чинить |
|---|---|---|---|
| **S0→S1** publish→pickup | sender вытеснен планировщиком; page fault; producer и sender на HT-сиблингах; сам `build_book` пишет 576 B | `perf sched latency`, счётчик `nivcsw`, трейс backlog'а ring'а | `isolcpus` + `taskset` на разные **физические** ядра; `mlockall` + prefault; SCHED_FIFO |
| **S1→S2** encode | branch miss на предикторе; промахи кэша по состоянию предиктора; **аллокация** | `perf stat -e cache-misses,branch-misses`; хук на malloc в debug-сборке | branchless-таблицы; состояние предиктора ≤ 1 кэш-линия на тип; всё предаллоцировано |
| **S2→S3** `sendmmsg` | `ENOBUFS`/`EAGAIN`; backpressure qdisc; **шейпинг AWS**; TX-очередь полна (Large LLQ вдвое режет ring до 512) | `ethtool -S \| grep allowance`; `tc -s qdisc`; счётчик `EAGAIN` | `SO_SNDBUF`; `tc qdisc replace dev eth0 root noqueue`; **понизить tier избыточности**; `ethtool -G tx` |
| **S3→S5** стек A + провод | джиттер фабрики; не тот AZ / нет placement group; ENA Express включён на низкой нагрузке (+десятки µs!); MTU/фрагментация на L3 | сравнить S3→S5 между двумя src-портами; `traceroute`; `ping -M do -s` | cluster placement group; выключить ENA Express; payload ≤1200 B на L3. **Именно эту стадию чинит хеджирование по путям** |
| **S5→S6** HW RX → `recvmmsg` | latency хардварного IRQ; softirq не запланирован; выход из C-state; переполнение RX ring; хоп через RPS-очередь | дельты `/proc/interrupts`, `/proc/softirqs`, `RcvbufErrors` | `napi_defer_hard_irqs` + `gro_flush_timeout` + `SO_PREFER_BUSY_POLL`; `ethtool -C rx-usecs 0`; `ethtool -G rx 4096`; выключить RPS; `intel_idle.max_cstate=1 idle=poll`. **Именно эту стадию чинит AF_XDP** |
| **S6→S7** decode + publish | реконструкция 576 B `OrderBook` = 576 B store на сообщение; промахи по дедуп-битмапу; стойло на THP-компактизации | `perf stat`, `compact_stall` из `/proc/vmstat` | non-temporal stores в слот; битмап размером под L2; `transparent_hugepage=madvise`, не `always` |
| **S7→S8** publish → consumer | **consumer залаплен** (особенно с `--csv`); consumer не запинен или на HT-сиблинге | наш счётчик `published` против `received` у consumer'а | запинить consumer; честно отчитаться о расхождении; патч `--csv` (см. ниже) |

| **Spread сконцентрирован в нескольких окнах по 100 мс** | steal time / шумный сосед / исчерпание burst-кредитов | steal из `/proc/stat`; `*_allowance_exceeded` | non-burstable размер инстанса; перепрогон; указать, какие окна исключены и почему |

### Три слоя инструментации (чтобы всегда-включённое было по карману)

| Слой | Что | Стоимость |
|---|---|---|
| **L1 — всегда** | Лог-линейные гистограммы (3 значащие цифры) на каждую стадию: `__builtin_clzll` + сдвиг + инкремент | ~1–2 нс на запись, 8 стадий ≈ 10 нс/сообщение ≈ **1% ядра при 1 M msg/s**. 128 КБ, влезает в L2 |
| **L2 — детерминированные сэмплы** | Полная запись всех стадий при `seq_id % S == 0`. **Ключевой трюк: выбор сэмпла — чистая функция от `seq_id`**, поэтому sender и receiver независимо выбирают *одни и те же* сообщения без единого бита на проводе. Джойн офлайн по `seq_id` | 64 B/запись, `S=64` при 1 M/s → 1 МБ/с; 30-секундный прогон = 30 МБ. Арена `mmap(MAP_POPULATE\|MAP_HUGETLB)`, сброс на диск только при выходе |
| **L3 — триггер по хвосту** | Кольцо на 4096 компактных записей (`seq` + дельты S1..S3 как u16 нс = 16 B) для **каждого** сообщения. При превышении порога — пометить на дамп | Ловит причинность, которую перцентили уничтожают: «скачку на 200 µs предшествовали 30 сообщений монотонно растущего backlog'а» |
| **L0 — счётчики раз в 100 мс** | Дельты `ethtool -S` (все `*_allowance_exceeded`, `queue_stop`, `missed_tx`), `/proc/net/snmp` `UdpInErrors`/`RcvbufErrors`, `/proc/interrupts` по ENA-очередям, `/proc/softirqs`, steal из `/proc/stat`, `getrusage` `nivcsw`/`majflt`, наши счётчики (лапы, `EAGAIN`, NACK, дедуп-хиты, текущий tier, глубина backlog'а) | На housekeeping-ядре. Превращает «был скачок» в «и вот почему» |

**Контроль возмущения.** Флаг `--instr {off,hist,hist+sample,full}` и **опубликованная таблица** p50/p99/p99.9/p99.99 на каждом уровне. Headline-числа берём на `hist` и показываем, что `off` совпадает в пределах шума.

**Корреляция на уровне датаграмм.** 4-байтный монотонный `dgram_id` в wire-хедере. Джойн по `dgram_id` — эффекты уровня датаграммы, по `seq_id` — уровня сообщения. Разделяет «датаграмма опоздала» и «сообщение опоздало внутри нормальной датаграммы».

### Часы: как измерять кросс-хост честно

Четыре независимых инструмента, все дешёвые:

1. `chronyc tracking` — offset, root delay, root dispersion. До и после каждого прогона.
2. `/sys/bus/pci/devices/<bdf>/phc_error_bound` — собственная оценка Nitro ошибки PHC.
3. **ClockBound** — интервал `(earliest, latest)` истинного времени на хост.
4. **Двунаправленный прогон** — самый сильный ход.

Полная граница: `CEB = |offset| + 0.5·root_delay + root_dispersion + phc_error_bound` на хост; парная граница = сумма. Печатать всё это в бандл результатов **каждого** прогона.

**Двунаправленная валидация (главный методический аргумент).** Гоняем весь пайплайн в обе стороны одновременно (A→B и B→A, независимые пары producer/consumer, разные порты). Пусть `c` — смещение часов A−B:
- `L_AB + L_BA` **точно свободно от смещения** — не требует предположения о симметрии пути. Любой конкурент, заявляющий 5 µs one-way, обязан предъявить сумму 10 µs.
- `(L_AB_изм − L_BA_изм)/2 = −c` при симметрии пути → независимая оценка смещения, сверяем с ClockBound. Совпали в пределах ~2 µs — история про часы доказана дважды.

Гигиена: `makestep 0 0` (никаких шагов) и низкий `maxslewrate` во время прогонов, прогоны 10–30 с. Слю 500 ppm за 60 с — это 30 µs дрейфа.

Ожидаемая точность PHC: смещение в единицах µs, 5/95 перцентили за 15 минут редко выходят за **±2 µs**, root dispersion 0.6–1.8 µs. Против one-way ~26 µs это ~8% смещения на p50 и **практически ноль на p99−p50**.

### Инжекция потерь

Два независимых инжектора, оба в результатах:

1. **Детерминированный дроппер внутри receiver'а**, ключ `hash(dgram_id) < threshold`. Точно воспроизводим, не зависит от версии ядра, и **судья воспроизведёт кривые потерь без root**.
2. `tc netem loss random 1%` и `tc netem loss gemodel` — реалистично, но зависит от ядра и недетерминировано.

Модель Gilbert-Elliott обязательна: реальные потери пачками, и именно пачки ломают одиночный parity.

### Ф0 — Измерительный фундамент (дни 1–2, 16 ч) — ВОРОТА G0

Это экзистенциальный риск: если нельзя надёжно измерить кросс-хост латентность, все 18 последующих дней оптимизируют шум.

### Эксперимент дня 2, определяющий стратегию

50 строк кода, 2 часа. Шлём парные пакеты с `(srcP1, dst)` и `(srcP2, dst)` спина к спине, штампуем оба прихода HW RX-таймстемпами, считаем CCDF для `L_A`, `L_B` и `min(L_A, L_B)`.

Зачем именно это, а не кривая потерь: результат «NACK против дублирования» **почти наверняка выйдет в нашу пользу — это арифметика**. Это headline-график, но не информация, он не изменит архитектуру. А независимость путей — по-настоящему неизвестна и **определяет архитектуру**:

- Если `min(L_A, L_B)` даёт p99.9 около p97 одиночного пути → один механизм (дублирование по двум портам) закрывает *разом*: восстановление потерь без RTT, хеджирование джиттера фабрики, разнесение по RX-очередям/ядрам против джиттера хоста, и тривиально композится с fan-out. Один механизм на все оси рубрики.
- Если вышло плоско (пути не независимы) → мы узнали на второй день, что хвост host-side, и 20 дней надо тратить на изоляцию, busy-poll и AF_XDP, а не на топологию избыточности.

**Практическая деталь:** нельзя предполагать, что два src-порта реально сели в разные RX-очереди. RSS у ENA хеш-based, `ethtool -N` может не работать. Робастно: на старте sender пробует кандидатов, receiver по control-каналу докладывает, в какую очередь/CPU каждый попал (по дельтам `/proc/interrupts`), выбираем пару на разных очередях. Измеряем, а не вычисляем.

### Ф4 — Восстановление потерь (дни 8–11, 32 ч) — HEADLINE

`transport/include/{redundancy.h,nack.h}`.

Сравнительная арифметика (база: one-way D ≈ 26 µs, RTT ≈ 52 µs, gap между датаграммами `g` ≈ 3 µs при 1 M msg/s):

| Схема | Оверхед | Задержка восстановления @1M | Остаточные потери, p=1% |
|---|---|---|---|
| NACK + ретрансмит | 1.0× | `T_detect + 2D` ≈ **57–65 µs** | 1e-4 требует 2-го раунда → **2 RTT ≈ 130 µs на p99.98** |
| Дублирование, 2 src-порта, Δ=0 | 2.0× | **0** (это `min` двух розыгрышей) | p² = 1e-4 |
| **2 порта + стаггер Δ=1** ⭐ | 2.0× | 3 µs (худшая копия) | p² = 1e-4, при пачках ≈1e-3 |
| **3 порта, стаггеры 0/1/3** ⭐⭐ | 3.0× | 0 / 3 / 9 µs | p³ = **1e-6**, при пачках ~1e-5 |
| XOR-окно k=8 | 1.125× | среднее 12 µs, худшее 27 µs | C(8,2)p² = 2.8e-3 |

**Как это читать.** При p=1% NACK-решение кладёт p99 на ~60–90 µs при p50 = 26 µs — трёхкратный взрыв хвоста, и происходит он **ровно на измеряемом перцентиле**. Дублирование держит p99 ≈ p50. Этот контраст и есть headline-график.

**Результат второго порядка, который никто не посчитает:** 2× дублирование оставляет остаток 1e-4 = **ровно граница p99.99**. То есть 2× чинит p99 и p99.9, но оставляет p99.99 ≈ RTT. **Чистый p99.99 при 1% потерь покупает только 3×** — и 3× от 40 B/сообщение при 1 M msg/s это всё ещё меньше 1 Gbps. Вот настоящая причина делать кодек: не ради сдвига точки насыщения, а чтобы 3× избыточность стала по карману.

- **Стаггер Δ выводится из измеренной гистограммы длин пачек потерь:** `Δ = ceil(p95 длины пачки) + 1`, с потолком `Δ·g ≤ 20 µs`. При `netem loss random` гистограмма скажет run=1 → **Δ=0, чистое хеджирование**. При `gemodel` скажет run≈3 → **Δ=3**. Одно число, выведенное из данных, делает всю адаптацию.
- **NACK как страховка:** детектор дыр с таймером терпимости к переупорядочиванию `T_d = 2 × измеренный разброс + запас` (при двух путях это ~15–25 µs, не 5 — **измерить, не угадывать**). Кольцо *закодированных* датаграмм на 200 мс = 8 МБ на hugepages. Heartbeat с `current_max_seq` раз в ~200 µs, чтобы ловить потерю в конце пачки.
- **Fan-out × NACK:** при unicast-репликации потери на трёх потоках **независимы** (разные 5-tuple) → **никакого подавления, ретрансмит только запросившему**. Подавление тут добавило бы латентность за ноль пользы. Сказать это в райтапе явно — многие рефлекторно реализуют SRM-подавление. Для multicast — коалесцирование ремонтов в окне 100 µs, не рандомизированные задержки SRM.
- **Защита от NACK-шторма:** token bucket ≤5% от прямого потока на получателя. **При превышении sender повышает tier избыточности вместо ретрансмита** — устойчиво тяжёлые потери автоматически переключают систему с реактивной на проактивную.

### Ф5 — Кодек (дни 12–13, 16 ч)

Два режима доставки, оба с опубликованными числами:

- **`--deliver exact` (по умолчанию, headline-числа):** receiver восстанавливает исходную структуру 192/192/576 B **побайтово**. Неоспоримо. Включает `--paranoid` с инлайновым `memcmp` и офлайновый fuzz-тест, гоняющий миллионы фреймов туда-обратно с проверкой байтового равенства.
- **`--deliver slim` (вторичный результат):** документированная схема v2 (`version = 2`, новые type id), выкидывающая только **классифицируемые** поля: производные (`notional`, `*_ticks`, `*_lots`, `prev_update_id`, `body_len`), константно-дублирующие (`match_engine_ts_ns == exchange_ts_ns`, четыре константные строки → 4-байтный instrument id + одноразовое словарное сообщение), reserved-паддинг. Обосновываем по классам. Это ещё и убирает ~500 B store на book-сообщение в стадии S6→S7 — реальный выигрыш латентности.

**Правило честности кодека — сформулировать в райтапе:**

> Предиктор может использовать только информацию, присутствующую в потоке сообщений: другие поля того же сообщения или предыдущие значения того же поля. Он никогда не кодирует константу, вычитанную из `producer.cpp`.

Правило реализуемо и **естественно исключает ровно тот случай, который судья назвал бы подгонкой под бенчмарк**: `checksum = (u32)(seq * 2654435761u)` из `producer.cpp:161` не берётся никаким генерическим предиктором → **шлём 4 байта явно**. Именно эта строка доказывает, что правило работает.

Каждый предиктор — «1 бит + проверка при кодировании + откат на явное значение при несовпадении». Шкала `price_ticks` **выучивается в рантайме** перебором {1,10,…,1e9} на первых N сообщениях и проверяется на каждом. Требует `-ffp-contract=off`, но verify-and-fallback делает нас корректными даже при нарушении. Для неизвестных типов — сырой/LZ4 fallback (README прямо говорит, что payload может смениться на «произвольные сообщения от единиц до сотен байт» — подогнанный кодек сломается, выучиваемый деградирует плавно).

Ожидаемо: Trade 192→~28 B, Bbo 192→~26 B, OrderBook 576→~60 B, **mixed 320 B → ~38 B (8.4×)**.

### Ф6 — Адаптивный контроллер (день 14, 8 ч)

Лестница из пяти tier'ов, **все входы измеримы локально, ни одной константы, привязанной к бенчмарку**:

| Tier | Триггер | Схема | Оверхед |
|---|---|---|---|
| 3 | `util < 25%` и (`loss ≥ 0.5%` или включена цель по p99.99) | 3 копии, порты A/B/C, стаггеры 0/1/3 | 3.0× |
| 2 | `util < 40%` (**по умолчанию**) | 2 копии, порты A/B, адаптивный Δ | 2.0× |
| 1 | `util 40–65%` | 1× + XOR(k); **урезать потолок батча**, чтобы `g` оставался ≤ 4 µs | 1.1–1.3× |
| 0 | `util > 65%` или растут `*_allowance_exceeded` | 1× + только NACK | 1.0× |
| −1 | backlog растёт **и** мы в tier 0 | сбрасываем избыточность **раньше**, чем данные; громко логируем | 1.0× |

Входы: `bytes_sent_100ms / link_budget`; дельты `ethtool -S` (жёсткий стоп-сигнал); частичные отправки `sendmmsg` / `EAGAIN` / `ENOBUFS`; **backlog producer-ring'а `producer_seq − our_last_consumed_seq` в слотах** (истинный сигнал «успеваем ли», он же ловит лапанье sender'а); телеметрия получателя раз в 20–50 мс (loss rate, **гистограмма длин пачек**, разброс переупорядочивания, восстановлено по NACK).

### Ф7 — Fan-out (день 15, 8 ч)

- N ≤ 4: один `sendmmsg` на неподключённом сокете, `[dst1..dstN]`, ~0.5–1 µs на назначение в ядре → перекос 1–3 µs между первым и последним. **Ротировать порядок назначений каждую датаграмму**, чтобы никто не был систематически последним.
- N > 4: по TX-потоку и сокету на получателя, каждый busy-polls тот же SHM ring (перекос → ~0.2 µs ценой N ядер).
- **Метрика перекоса между получателями** — этого не покажет никто.
- Режим `--transport udp-mcast` для их «реального L2 стенда»: fan-out становится O(1) по стоимости sender'а, а FEC разделяется между получателями.
- Мерить обе топологии: 3 получателя на 3 хостах и 3 на одном (разные порты + разные имена SHM). Это разные бутылочные горлышки (общий NIC против общей фабрики), показать понимание разницы.

### Ф9 — AF_XDP (дни 17–18 или 8 ч жертвенных, по ветке G1)

ENA поддерживает native AF_XDP с zero-copy: введено в r2.7.0, переоткрыто в **r2.13.0**, расширено в r2.16/2.17. Использовать ≥ r2.16. Ограничения: нужен загруженный XDP-программа; только 4 КБ буферы; MTU ≤ 3502; **ZC-каналы только с индексом очереди < половины максимума** (32 канала → ZC только на 0–15).

Скрытая стоимость, которую никто не закладывает: AF_XDP обходит ARP/маршрутизацию/ICMP — Ethernet+IP+UDP заголовки и разрешение ARP пишем руками. Это ~день работы с нулевым выигрышем по латентности.

**Делать только после** `SO_BUSY_POLL` + `SO_PREFER_BUSY_POLL` + `napi_defer_hard_irqs`/`gro_flush_timeout`, которые дают большую часть того же эффекта с нулевым риском воспроизводимости. Интересный вопрос не p50 (оценка выигрыша 1–3 µs), а **режет ли AF_XDP p99.9**, убирая softirq-планирование из RX-пути — измеряем именно стадию S5→S6. Таймбокс: бросаем в конце дня независимо от результата.

### Ф12 — Репетиция воспроизводимости + head-to-head (день 20, 8 ч)

Поднять чистые инстансы, следовать **только своему** `docs/REPRODUCE.md`, запускать **только свой** скрипт. Всё, что требует что-то вспомнить, — баг.

- `bench/run_all.sh` работает **без root и без тюнинга** и выдаёт полный бандл. Затем `bench/tune.sh` требует root. Публикуем оба набора чисел — судья может не применить наш тюнинг, дефолт обязан быть хорош.
- **Порядок запуска задокументировать точно:** receiver (создаёт ring) → consumer (`--from-edge`) → sender → producer.
- Прогнать публичный Claude-бейслайн на нашем стенде и положить его референсной линией на каждый график.
- В каждый бандл автоматически: тип/размер инстанса, AZ, placement group, AMI id, версия ядра, версия ENA-драйвера, карта ядер, `chrony.conf`, `chronyc tracking`, `phc_error_bound`, `ethtool -S/-i/-c/-g/-k`, `/proc/cmdline`.

## Что мы НЕ делаем и почему (это идёт в райтап)

| Не делаем | Причина |
|---|---|
| DPDK | ~2–4 µs из 26 µs пути ценой высокого риска DQ. Приводим опубликованное число AWS как потолок |
| Reed-Solomon | Recovery latency ограничена снизу временем набора окна; выигрывает только при дефиците полосы, куда мы не попадаем. Анализ — да, код — нет |
| TGW multicast | ~150–200 µs one-way; AWS сам не рекомендует для HFT |
| ENA Express по умолчанию | +десятки µs к медиане на низкой нагрузке. Один эксперимент на насыщении, результат в таблицу |
| SRM-подавление NACK при unicast | Потери на разных 5-tuple независимы → подавление добавит латентность за ноль пользы |
| Патч `consumer.cpp` без предъявления доказательств | **Сначала** измеряем возмущение (p99.99 с `--csv` и без, на немодифицированном бинаре), **потом** предлагаем ~12-строчный патч отдельным помеченным диффом, и **все headline-числа даём в обоих вариантах** |

**Запрещено себе:**
- Любое улучшение, полученное доставкой меньшего числа сообщений.
- Непоследовательное использование `--from-edge` или обрезка прогрева без раскрытия.
- Константы, подогнанные под конкретный rate бенчмарка (адаптивность без ручек — и лучше инженерно, и лучше выглядит).
- Кодирование констант, вычитанных из `producer.cpp`.

## Риски

| Риск | Уровень | Митигация |
|---|---|---|
| Не работает кросс-хост измерение (PHC не поднимается / clocksource = `kvm-clock`) | **Экзистенциальный** | Ворота G0 на день 2. Двунаправленная сумма как fallback — она вообще не требует PTP |
| Прогон у судей не заводится | **Высокий** | v0 замораживается на день 4 и всегда зелёный. `run_all.sh` без root. Репетиция на чистых инстансах, день 20. Ring по умолчанию 1024 слота |
| Sender лапается на producer-ring под нагрузкой | Средний | Backlog `producer_seq − our_last_consumed` как первоклассная метрика и вход контроллера; tier −1 сбрасывает избыточность раньше данных |
| Consumer лапается нашим receiver'ом (особенно с `--csv`) | Средний | Всегда репортим наш `published` рядом с их `received`, чтобы отделить наши потери от их отставания |
| Дубликаты ломают метрики | Средний | Дедуп в v0, юнит-тест, `received == expected` как assert в regress-скрипте |
| Пути по разным src-портам оказались зависимы | Средний | Именно это и проверяет эксперимент дня 2; ветка B плана готова |
| Спот-прерывание в середине матрицы | Низкий | Финальную матрицу гоняем на on-demand, не на spot |

## Верификация

**Юнит-уровень** (`make -C transport test`, гоняется на каждом коммите):
1. `test_codec` — fuzz round-trip: миллионы сгенерированных фреймов, `memcmp` исходного и восстановленного == 0 для `--deliver exact`.
2. `test_dedup` — дубликаты и переупорядочивание не приводят к двойной публикации.
3. `test_redundancy` — при принудительной потере копии A сообщение восстанавливается из копии B; при потере обеих генерится NACK.

**Функциональный e2e на одном хосте** (`bench/regress.sh`, гоняется на каждом коммите):
```
receiver → consumer --from-edge → sender → producer --count 1000000
```
Проверяем: `received == count`, `dropped == 0`, наш `published == received` у consumer'а, и p50/p99/p99.9 не хуже сохранённого бейслайна больше чем на порог. Это ловит регрессии без AWS.

**Кросс-хост** (`bench/run.sh`, после каждой фазы): полный бандл результатов + строка в таблицу прогресса ноутбука. `env_check.sh` отказывается стартовать на нетюненном окружении, чтобы случайно не сравнить яблоки с апельсинами.
